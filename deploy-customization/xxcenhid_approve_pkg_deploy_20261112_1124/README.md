- A shell on the TARGET application tier as the applications owner, with its environment file (`EBSapps.env`).
- The APPS password (asked for, or `export APPS_PWD=...`). It never appears on a command line, except for XDOLoader steps, which have no password prompt.

## Manual deployment, step by step (no CI/CD pipeline)

Follow these in order. Every command runs from the bundle folder unless it says otherwise.

### A. Prepare the bundle (in SQLTools, on your desktop)

1. In Deploy Customization, review the object list and **Review & Generate** into a folder.
2. **Fetch the files only the source tier has** (FNDLOAD / WFLOAD definitions, server files). Either use **Download AOL Files** in SQLTools, or copy the folder to the SOURCE application tier and run:
   ```
   . <source environment file> run
   ./download.sh <environment file> run
   ```
   Copy every file reported `@@OK` back into the bundle folder. Any `@@FAIL` must be fixed first.
3. Click **Make Zip** (or zip the folder yourself). Keep a copy, or **Publish to Git**, so you know exactly what was deployed.

### B. Copy it to the TARGET application tier

1. Copy the zip and unpack it as the applications owner (for example `applmgr`):
   ```
   scp XXCENHID_APPROVE_PKG.zip applmgr@<target-host>:/tmp/
   ssh applmgr@<target-host>
   cd /tmp && unzip -o XXCENHID_APPROVE_PKG.zip && cd XXCENHID_APPROVE_PKG
   chmod +x deploy.sh download.sh
   ```
2. Check that every file arrived: `./deploy.sh -l` lists the steps.

### C. Before changing anything

1. Agree a deployment window. Hotpatch deploys into the running system; plan for a quiet period.
2. **Ask the DBA for a guaranteed restore point** (or a copy of the tables this bundle changes). This is the only complete undo for table and data changes.
3. Validate. This changes nothing:
   ```
   ./deploy.sh -e <environment file> -v
   ```
4. Read `logs/validation.txt` and fix every item under *Problems*. Review *Warnings*, the *Changes the deployment makes*, and the *Rollback* section, which shows which steps can only be undone by hand.

### D. Deploy

1. Run:
   ```
   ./deploy.sh -e <environment file>
   ```
   Enter the APPS password when asked. Each step prints `ok`, `unchanged, skipped` or `FAILED`.
2. **If a step fails**, read `logs/<file>.log`, then choose:
   - fix the cause and resume: `./deploy.sh -e <environment file> -s N` (N is the failed step), or
   - undo the steps already deployed: `./deploy.sh -e <environment file> -r`, then do the "by hand" items listed in `logs/rollback.txt`.
   Do not run it again without `-s`: that is refused, because it would overwrite the backups.

### E. Verify

1. **Read `logs/invalid.txt`.** deploy.sh lists the invalid objects in the whole database before and after deploying. Objects that were valid before and are invalid now were broken by this deployment's changes (a cascading effect), so it recompiles them once. The report lists the ones that recompiling fixed, the ones still invalid with their compile errors, and what to do. An exit code of 5 means some are still invalid: fix the dependent object, restore compatibility or add the missing grant, then recompile, or roll back with `-r`. Objects that were already invalid before are counted separately; this deployment did not cause them.
2. Compile any forms the deploy log names (`NOTE: compile the form: frmcmp_batch ...`).
3. Test in the application: run the concurrent programs, open the forms and menus, run the reports. Log out and back in to see menu and profile changes. For OA Framework changes, clear the cache in Functional Administrator.
4. Keep the whole `logs/` folder with the change record. It holds the backups that a later rollback needs.

### F. If you need to roll back later

1. From the same folder (with its `logs/`), run `./deploy.sh -e <environment file> -r`.
2. Do each "BY HAND" item in `logs/rollback.txt` (see the table below).
3. Verify again as in step E.

`./deploy.sh -l` lists the steps with their numbers.

## Rollback

Validation saves what the target has now before anything is deployed, and each step deployed is recorded in `logs/done.txt`. `./deploy.sh -e <environment file> -r` undoes those steps, last first, and writes `logs/rollback.txt`.

- **Undone automatically:** packages, types, procedures, functions, triggers and views (the previous DDL is run again, or a new object is dropped); FNDLOAD / WFLOAD objects (the saved definition is uploaded again); server files (the old file is copied back, or a new one removed).
- **Undone by hand:** tables, indexes, data, grants, synonyms, sequences and XML Publisher files. Undoing them automatically could lose data written since the deployment, so `logs/rollback.txt` says what to do for each. New FNDLOAD objects cannot be deleted by FNDLOAD: disable or end-date them.
- **Full undo of table / data changes:** a guaranteed restore point or Flashback Table taken before deploying, by the DBA.

## Unattended runs (CI/CD)

- Set `APPS_PWD`, and `SCHEMA_PWD_<SCHEMA>` if validation asks for one, from the pipeline's secrets.
- Gate with `./deploy.sh -e "$ENV_FILE" -v`, then deploy with `./deploy.sh -e "$ENV_FILE" -R`.
- Keep `logs/` as the job's artifact.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Done (or validation passed / rollback done) |
| 1 | A step failed |
| 2 | Usage or environment problem, failed APPS login, or a failed run not resumed |
| 3 | Validation failed: nothing was changed |
| 4 | Rollback of a step failed |
| 5 | Deployed (or rolled back), but objects valid before are invalid now: see `logs/invalid.txt` |

## Editing deploy.sh by hand

Generating the bundle again rewrites `deploy.sh`, `lib/` and this README. A step added by hand has no validation check and no automatic rollback: it is listed as "by hand" in `logs/rollback.txt`.
